랭킹이 있는 순간 클라이언트가 보고한 숫자를 그대로 믿을 수 없다. 이번 단계는 서버를 세우고 "서버가 정본"으로 뒤집는 작업이었다.

## 무엇을

- FastAPI + PostgreSQL 백엔드. 앱 4개: `hub`(앱 간 계약만), `auth`(게스트 계정·JWT), `save`(세이브 복원·동기화), `masterdata`(밸런스 계수).
- 게스트 계정: 기기가 만든 난수 ID로 `POST /auth/guest`를 부르면 계정을 만들거나 찾고 토큰을 준다. 로그인 화면 없이 바로 시작한다.
- 클라우드 세이브: 시작 시 `GET /save`로 서버 세이브를 받고, 오프라인 보상은 **서버 시간**으로 서버가 계산해 더해 준다. 30초마다 `PUT /save`로 올린다.
- 델타 검증: 직전 서버 상태 → 새 상태의 변화가 경과 시간 안에 가능한지 본다. 실패하면 저장하지 않고 서버 상태를 돌려주며, 클라이언트는 그 상태로 롤백한다.
- 밸런스 계수는 서버 JSON이 정본이고 클라이언트는 버전을 보고 캐시한다. 앱 업데이트 없이 수치를 고칠 수 있다.

## 왜 이렇게

- **완전 서버 권위(전투를 서버에서 돌리기)는 택하지 않았다.** 1인 개발과 무료 범위 인프라에서 무리다. 대신 클라이언트가 돌리고 서버가 상한만 검사한다. 상한은 정직한 플레이가 절대 걸리지 않을 만큼 느슨하고, 조작은 그 배수 이상 이득을 못 본다.
- **검증 규칙 세 가지.** ① 레벨·최고 스테이지·누적 처치는 줄지 않는다 ② 처치 수 ≤ 경과 시간 × 공격속도 × 1.5 ③ 골드 보존: 새 골드 + 쓴 골드 ≤ 이전 골드 + 벌 수 있는 최대 골드. 골드 상한은 "모든 처치가 최고 스테이지 보스였다"는 가정이라 실제의 10배까지 봐준다. 메이플 키우기가 매크로와 핵으로 겪은 일을 보면 이 정도 그물이라도 없는 것과는 다르다.
- **오프라인 보상을 서버 시간으로 옮기니** 2주차의 시계 조작 검사가 통째로 사라졌다. 보상은 `synced_at`을 지금으로 옮기며 저장하므로 두 번 받을 수 없다.
- **시작 시 로컬이 서버보다 앞서 있으면 어쩌나.** 앱이 마지막 동기화 전에 죽었을 때다. 로컬을 먼저 올리면 서버가 계산할 오프라인 보상이 사라지고, 서버를 먼저 받고 로컬을 올리면 델타 검증에 걸린다. 서버를 정본으로 두고 최대 30초의 진행을 버리는 쪽을 택했다. 30초는 자동 저장 주기이고, 백그라운드 진입 시에도 저장하므로 실제로 잃는 경우는 드물다.

## 어떻게

- 구조는 redoceanmap 백엔드를 그대로 따랐다. 앱 내부는 헥사고날(adapter → app → domain), 앱 사이는 허브-스포크, 유스케이스 하나에 라우터·스키마·DTO·포트·인터랙터·프로바이더·테스트가 각 1개. import-linter 계약 5종이 이걸 기계로 강제한다.
- `save`는 계수를 `masterdata`에서 직접 가져오지 않는다. 허브에 `BalancePort`를 두고 `masterdata`가 구현, `save`가 소비, `main.py`가 둘을 잇는다. 스포크끼리 서로를 모른다.
- 공식(HP = 10 × 1.18^stage 등)은 Dart와 Python 양쪽에 있다. 계수만 서버가 소유하고 공식은 양쪽이 내장하는 게 "계수 단일 소유" 원칙이다. 두 구현이 갈리지 않도록 같은 입력으로 같은 값이 나오는지 교차 테스트를 뒀다.
- 검증은 테스트 49개(도메인·인터랙터 스텁·API 배선)와 실제 Postgres에 대한 curl 왕복, 그리고 맥 앱을 서버와 함께 띄워 45초 동안 로그인 → 복원 → 동기화가 DB에 남는 것까지 확인했다.

## 아쉬운 점

- 검증을 통과했더라도 골드 상한이 10배라 정교한 조작은 못 잡는다. 랭킹이 붙을 때 처치당 실제 보상 기준으로 조인다.
- JWT는 HS256 단일 비밀이다. 발급 프로세스를 분리하는 날 RS256으로 옮긴다.
- 맥에서 8000번 포트를 다른 프로젝트의 VS Code 포워딩이 쥐고 있어서 8010으로 비켰다. 한 기기에서 프로젝트 둘을 돌리면 이런 게 계속 나온다.
